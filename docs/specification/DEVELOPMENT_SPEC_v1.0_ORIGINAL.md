# PRESTIQUE Workspace — 프로그램 개발 명세서

> **문서 유형:** 제품 요구사항 정의서(PRD) + 소프트웨어 요구사항 명세서(SRS) + 기술 설계 기준서
>
> **문서 버전:** 1.0  
> **기준일:** 2026-11-17  
> **대상:** 기획자, 프런트엔드·데스크톱 개발자, QA, 향후 백엔드·보안 담당자  
> **프로젝트 성격:** 로컬 우선(Offline-first) 기업용 Markdown 문서·지식관리 시스템
>
> **범위 제한:** 색상, 타이포그래피, 레이아웃, 아이콘, 애니메이션 등 **시각 디자인 지침은 포함하지 않는다.** 본 문서의 화면·작업흐름 언급은 기능·행위에 관한 요구사항이다. 별도 디자인 명세서와 충돌할 경우 UI 표현은 디자인 명세서, 데이터와 동작은 본 문서를 우선한다.

---

## 1. 프로젝트 개요

### 1.1 개발 목적

PRESTIQUE Workspace는 회사가 생산하는 프로젝트 문서, 연구노트, 실험일지, 회의록, 사업계획서, 운영 문서 및 각종 첨부파일을 **사용자 소유의 Markdown 파일 중심으로 관리**하는 프로그램이다.

- 초기: 별도 서버 없이 Windows PC에서 독립 동작하는 데스크톱 프로그램 제공.
- 병행: GitHub Pages 또는 동급 정적 호스팅에 올릴 수 있는 **웹 앱/PWA** 제공. 모바일에서는 Markdown 문법 없이도 문서와 사진을 작성.
- 확장: 로컬 네트워크 또는 클라우드 기반의 문서 동기화, 계정·권한, 전자결재, 감사 이력, AI/RAG 연결.
- 원칙: 공급사나 전용 DB에 종속되지 않도록 Markdown·첨부파일의 독립성·이식성을 보장.

### 1.2 핵심 의사결정(확정)

| 항목 | 결정 |
|---|---|
| 기본 데이터 원본 | UTF-8 `.md` 파일 + 상대경로로 연결된 첨부파일 |
| PC 저장 | 사용자 지정 워크스페이스 디렉터리(로컬 파일 시스템) |
| PC 메타데이터 | SQLite(검색 인덱스 및 재구축 가능한 부가정보) |
| 브라우저 저장 | IndexedDB/필요시 OPFS, 사용자 내보내기로 백업 가능 |
| PC 실행환경 | Windows 우선, macOS/Linux는 후속 호환 검토 |
| 브라우저 앱 | 정적 빌드 배포 및 HTTPS, 모바일 반응형 기능 |
| 모바일 편집 | WYSIWYG 기본, Markdown 원문 편집은 선택 기능 |
| 웹 호스팅 | 웹 **프로그램 코드**만 정적 배포; 사내 문서는 배포물에 포함 금지 |
| 동기화 | V1에 없음; V2에서 명시적 동기화 엔진 도입 |
| 로그인 | 개인 로컬 사용 V1에 불필요; 공유 서버 도입 시 필수 |
| 디자인 | 본 명세서에서 제외 |

### 1.3 용어

- **워크스페이스(Workspace):** 독립된 최상위 문서 저장소 1개.
- **프로젝트(Project):** 업무 단위의 상위 관리 대상. 내부에 중첩 폴더와 문서를 포함.
- **폴더(Folder):** 파일 시스템에 대응하는 문서 분류 단위.
- **문서(Document):** 안정적인 문서 ID를 가진 Markdown 파일.
- **첨부파일(Asset):** 문서에 연결된 사진·이미지·PDF 등 바이너리 파일.
- **로컬 우선(Offline-first):** 저장의 성공 여부가 네트워크 가용성에 의존하지 않는 방식.
- **시각적 편집(WYSIWYG):** Markdown 기호를 직접 입력하지 않고 서식 명령으로 문서를 작성하는 방식.
- **정적 호스팅:** HTML·CSS·JS 배포 방식. 서버 DB·로그인·파일 동기화를 자체적으로 제공하지 않음.
- **게시(Publish):** 명시적으로 승인한 문서만 공개 가능한 정적 콘텐츠로 내보내는 행위. 일반적인 웹 앱 배포와 별개.

### 1.4 구현 범위 구분

| 단계 | 대상 | 목표 |
|---|---|---|
| **V1 — 초기 출시** | 로컬 PC 앱 + 웹/PWA 독립 저장 | 프로젝트/폴더, Markdown, 이미지 첨부, MD 입출력, PDF, 검색, 자동저장, 단일 기기 오프라인, 프로젝트 백업·가져오기 |
| **V1.5 — 문서관리 강화** | PC·웹 | 버전 이력, 비교·복원, 템플릿, 내부 링크·백링크, 태그, 선택적 정적 문서 게시 |
| **V2 — 동기화** | PC·모바일·서버 | 동기화 서버, 계정, 충돌 처리, 백업, 여러 기기 동일 데이터 접근 |
| **V3 — 기업 협업** | 조직 | 역할·접근권한, 승인·개정·잠금, 감사 로그, 전자결재 |
| **V4 — 지식 활용** | AI 연계 | RAG 인덱싱, 출처 포함 검색·요약, 승인된 문서 범위의 AI 에이전트 연동 |

> **중요 제약:** V1의 PC 워크스페이스와 모바일 PWA 저장소는 **자동으로 연결되지 않는다**. 두 기기에서 같은 문서를 보려면 V1에서는 프로젝트 내보내기/가져오기를 사용하고, 실시간에 가까운 자동 동기화는 V2에서 제공한다.

## 2. 제품 기능 요구사항

### 2.1 요구사항 표시

- **P0:** V1 출시 필수
- **P1:** V1.5 권장
- **P2:** V2 이후 확장
- **AC:** 테스트 가능한 인수 조건(Acceptance Criteria)

**AC-WS:** 프로젝트 A > 연구 > 2026 폴더를 생성하고 문서 2개를 이동한 후 앱을 종료·재실행해도 위치·본문이 유지되어야 한다. 삭제 후 복원 시 문서와 링크된 첨부파일을 회복해야 한다.

**편집 모드:** PC는 원문 편집과 시각적 편집을 모두 제공한다. 모바일은 시각적 편집을 기본으로 하고, Markdown 원문 모드와 코드 블록 편집도 접근 가능해야 한다.

**중요:** Markdown 표현이 불가능한 독자적 블록을 V1에 무리하게 넣지 않는다. 표준 Markdown으로 직렬화가 불가능한 상태가 생기면 저장 전 명확한 안내가 필요하다.

**AC-DOC:** 모바일에서 문서 작성 → 제목·표·체크리스트·이미지 삽입 → Markdown 내보내기 → PC에서 재가져오기 시 지원 범위 내의 모든 의미적 서식과 참조가 유지되어야 한다.

**입력 처리:** 브라우저의 파일 입력 `accept="image/*"` 및 `capture` 지원 여부를 이용하되, 기기/브라우저별로 카메라 동작이 다를 수 있으므로 일반 파일 선택을 항상 대체 수단으로 제공한다.

**이미지 저장 정책:** 기본적으로 이미지 파일을 따로 저장하고 문서에는 상대경로 링크를 기록한다. 사진 크기를 줄여 저장할지 원본을 보관할지는 설정 가능하도록 데이터 모델을 준비한다. 변환은 사용자 동의 또는 설정에 따라 수행하고 원본 제거 정책을 명시한다.

**개인정보:** 이미지 EXIF(위치정보 등) 제거 옵션을 제공하고, 민감 사진을 원치 않는 외부 서버로 전송하지 않는다.

**AC-MOB:** 네트워크를 끊은 상태에서 스마트폰으로 텍스트 300자 및 사진 3장을 저장하고 PWA를 재실행해도 문서와 사진이 남아 있어야 한다. 단, 브라우저 데이터 삭제나 저장 공간 회수는 앱이 완전히 통제할 수 없으므로 이를 사용자에게 고지하고 ZIP 백업 경로를 제공한다.

**가져오기 보안:** ZIP 압축 해제 시 Zip Slip(상위 디렉터리 경로 탈출), 심볼릭 링크, 파일 개수 폭증, 압축 해제 후 과도한 용량 등을 차단한다.

**AC-FILE:** 문서 10개와 첨부파일 20개를 ZIP으로 내보낸 다음 깨끗한 워크스페이스로 가져오면 전체 수량 및 SHA-256 해시가 일치하고 상대링크가 유효해야 한다. (문서 ID 재발급 정책이 적용되는 경우 해당 metadata 파일만 예외 처리 가능)

**AC-PDF:** 한글 제목, 표 2개, 이미지 3개, 코드 블록 1개로 된 문서를 PDF로 저장했을 때 내용 누락·줄 겹침·한글 깨짐이 없어야 한다.

### 2.7 검색·분류

| ID | 요구사항 | 우선순위 |
|---|---|---|
| SEARCH-001 | 현재 워크스페이스의 문서 제목·본문 검색 | P0 |
| SEARCH-002 | 프로젝트·폴더 범위 필터 | P0 |
| SEARCH-003 | 검색 결과에 문서명, 소속 경로, 일치 부분 제공 | P0 |
| SEARCH-004 | 외부 변경 또는 가져오기 후 인덱스 다시 생성 | P0 |

**구현 주의:** PC는 SQLite FTS5를 검토한다. 한국어 검색 품질(부분 일치, 조사, 복합어)은 기본 토크나이저만으로 충분하지 않을 수 있으므로 별도 한국어 표본 테스트를 통과한 방식(예: n-gram 보조 인덱스)을 선정한다. 브라우저는 IndexedDB 기반 검색 인덱스를 별도 구현한다. 인덱스는 원본 파일을 이용해 언제든 재구축 가능해야 한다.

### 2.8 문서 템플릿·버전·링크(V1.5)

- **TPL-001:** 회의록, 연구노트, 실험일지, 업무보고서, 사업계획서, 품의서 등의 사용자 정의 템플릿.

- **VER-001:** 저장 시점별 스냅샷 또는 변경 이력 생성(사용자 설정에 따른 주기·보존정책).
- **VER-002:** 과거 버전 조회·차이 비교·새 버전으로 복원; 과거본 직접 덮어쓰기 금지.

### 5.2 문서 Front Matter 규약

```markdown
---
prestique_id: "01JXXXXDOCUMENTID"
title: "아보카도 추출물 실험일지"
created_at: "2026-11-17T10:00:00Z"
updated_at: "2026-11-17T11:30:00Z"
status: "draft"
tags: ["R&D", "아보카도"]
---

# 아보카도 추출물 실험일지

시료 준비 및 관찰 결과를 작성한다.

![껍질 시료](assets/01JXXXX-sample.webp)
```

**ID 정책**

1. 새 문서마다 전역적으로 충분히 충돌 가능성이 낮은 고유 ID(예: UUIDv7 또는 ULID)를 발급한다.
2. 파일의 이름이나 이동 경로를 ID로 쓰지 않는다.
3. 일반 Markdown 파일을 가져오면 필수 메타데이터를 추가할 수 있도록 사용자에게 처리 결과를 알린다.
4. 외부 파일에 이미 같은 `prestique_id`가 존재하고 내용이 다른 경우 자동 덮어쓰지 않고 가져오기 충돌 처리한다.
5. `catalog.json`과 front matter가 불일치하면 원본 내용 보존을 최우선으로 하고 복구 보고서를 생성한다.

**문서의 진실 공급원(source of truth):** 본문은 `.md`, 재구축 가능한 인덱스는 SQLite. 제목 등 교환 가능한 메타데이터는 front matter 및 휴대용 catalog로 관리하되 충돌 시 결정 규칙을 구현한다.

### 5.3 첨부파일 참조

- Markdown에서는 가능한 한 표준 상대경로를 사용: `![시료 사진](assets/01JXXXX-sample.webp)`.
- 업로드 파일명은 충돌 방지를 위해 ID 접두사 + 정제된 원본명 사용.
- 첨부파일은 디스크에 1회 보관하고 문서별 참조 관계를 메타데이터로 추적할 수 있어야 함.
- 문서 이동으로 상대경로가 변경되는 경우 관련 링크를 갱신하거나 첨부도 함께 이동해야 함.
- 외부 URL 이미지와 로컬 자산은 구분하고, 외부 이미지는 사용자가 명시적으로 요청하지 않는 한 자동 다운로드하지 않음.
- 허용 MIME 형식: 기본 이미지 JPEG/PNG/WebP/GIF(정적 또는 애니메이션), 첨부 PDF 및 일반 자료 파일. SVG는 보안 검토 후 별도 허용. 실행파일·스크립트는 기본 차단 또는 단순 바이너리 보관만 허용(미리보기 실행 금지).
- 파일 크기 한도는 기기 저장소별로 설정 가능하며 기본값은 운영 테스트 후 확정. 브라우저 업로드의 최대 크기를 무제한으로 가정하지 않음.

### 5.4 로컬 SQLite 예시 스키마

> 아래는 개념 스키마이며 실제 구현에서는 마이그레이션 도구, 외래키, 인덱스, 저장소별 물리 모델을 확정한다. 원본 MD가 유지되는 한 캐시는 재구축할 수 있어야 한다.

```sql
CREATE TABLE documents (
    id              TEXT PRIMARY KEY,
    workspace_id    TEXT NOT NULL,
    project_id      TEXT NOT NULL,
    relative_path   TEXT NOT NULL,
    title           TEXT NOT NULL,
    status          TEXT NOT NULL DEFAULT 'draft',
    revision        TEXT NOT NULL,
    checksum        TEXT NOT NULL,
    updated_at      TEXT NOT NULL,
    is_deleted      INTEGER NOT NULL DEFAULT 0,
    UNIQUE(workspace_id, relative_path)
);

CREATE TABLE assets (
    id              TEXT PRIMARY KEY,
    workspace_id    TEXT NOT NULL,
    relative_path   TEXT NOT NULL,
    mime_type       TEXT NOT NULL,
    byte_size       INTEGER NOT NULL,
    checksum        TEXT NOT NULL
);

CREATE TABLE document_assets (
    document_id     TEXT NOT NULL,
    asset_id        TEXT NOT NULL,
    PRIMARY KEY (document_id, asset_id)
);

-- 검색 인덱스 구조는 한국어 검색 실험 후 최종 확정.
-- FTS5 자체는 기본 선택지이며 언어별 토크나이저 검증 필요.
```

### 5.5 브라우저 저장 구조

- IndexedDB object store: `workspaces`, `projects`, `folders`, `documents`, `assets`, `settings`, `export_history`, `drafts`.
- IndexedDB에는 본문 Markdown, 메타데이터, 사진 Blob 등을 저장할 수 있다.
- 대용량 Blob 및 파일 접근 성능이 필요하면 OPFS 도입을 검토하되, iOS/Android/브라우저 호환성을 사전 테스트한다.
- PWA 설치, Service Worker 캐시, 문서 DB 저장은 서로 독립적으로 관리한다.
- `navigator.storage.persist()` 등의 영속 저장 요청을 고려하되 **브라우저 저장소는 사용자 데이터 삭제/정책 변화에 영향을 받으므로 유일한 백업으로 간주하지 않는다**.
- 내보내기 파일은 사용자가 직접 다운로드·보관하도록 지원한다.

### 5.6 메타데이터 마이그레이션

- 모든 워크스페이스 스키마는 `schema_version`을 가진다.
- 새 버전은 구버전 데이터를 백업한 뒤 업그레이드.
- 마이그레이션 실패 시 자동 복구 또는 읽기 전용 모드에서 백업·내보내기를 제공.
- DB 삭제 또는 캐시 손상 시 `.md` 및 `.prestique`로부터 재색인.
- 낮은 버전 앱에서 높은 버전 워크스페이스를 열면 데이터 손상을 막기 위해 읽기 전용 또는 명시적 거부.

## 6. 저장·무결성·충돌 처리

### 6.1 로컬 저장 프로세스

1. 사용자가 편집을 시작하면 메모리의 문서 초안 상태 변경.
2. 디바운스 후 Markdown으로 직렬화; 지원하지 않는 콘텐츠인지 검증.
3. 저장 전 디스크의 현재 revision/checksum을 조회해 외부 수정 확인.
4. 충돌이 없으면 같은 디렉터리의 임시파일에 저장하고 가능한 환경에서 flush/fsync 실행.
5. 원자적 rename/replace 사용(운영체제별 보장과 실패 시나리오 테스트).
6. 파일 저장에 성공한 후 catalog·SQLite 색인 갱신.
7. 색인 실패만 발생하면 문서는 유지하고 재색인 작업을 예약.
8. 저장 완료 상태는 실제 파일 영속 저장을 확인한 뒤 표시.

**저장 실패:** 디스크 부족·권한 오류·외부 삭제 등은 침묵하지 않는다. 저장 실패 시 메모리 초안/복구 영역을 보존하고 문제를 사용자에게 알린다.

### 6.2 외부 프로그램에서 수정한 파일

- PC 워크스페이스 파일 변화를 파일 감시자로 감지.
- 편집 중이지 않은 문서: 외부 변경을 다시 읽어 UI와 인덱스 갱신.
- 앱에서 편집 중인 문서: 외부 변경이 감지되면 **앱의 버전과 외부 버전을 비교**, 자동 덮어쓰기 금지.
- 충돌 처리 선택지: 내 변경 유지 / 외부 변경 수용 / 둘 다 복제하여 보존. V1에서는 복제 보존을 안전 기본값으로 한다.
- 감시 이벤트가 유실될 수 있으므로 앱 시작·포커스 복귀·사용자 새로고침 시 스캔.

### 6.3 삭제 및 백업

- 삭제는 기본 휴지통 이동으로 처리하며 파일을 즉시 영구 삭제하지 않는다.
- 휴지통에서 원위치 복구 및 충돌 시 복구 위치 선택 지원.
- 파일 버전 이력과 프로젝트 백업은 별개 기능이다.
- V1 필수: 프로젝트 ZIP 내보내기·가져오기, 로컬 저장 실패 방지, 비정상 종료 초안 복구.
- V1.5: 자동 스냅샷·정기 백업(백업 드라이브는 별도 위치 권장), SHA-256 검증 및 복구 연습.
- 백업 시 단순히 파일을 복사했다는 이유만으로 무결성을 보장했다고 표시하지 않는다. 백업 파일 열기·해시 검증 수행.

### 6.4 버전 정책(V1.5 이후)

- 문서 수정 시 버전 ID, 시간, checksum, 작성 주체(로컬 사용자 또는 계정) 기록.
- 변경 전·후 diff 제공, 복원 시 과거 스냅샷을 새 버전으로 생성.
- 버전별 첨부파일 참조 보존 정책 확정.
- 저장 용량 상한·보존기간·자동 정리 정책은 사용자 설정 및 정책 문서에서 명시.

## 7. Markdown 규격·편집기 계약

### 7.1 V1 지원 문법

**기본 규격:** CommonMark + 구현·테스트로 확인된 GitHub Flavored Markdown(GFM) 부분집합.

| 요소 | V1 지원 | 비고 |
|---|---|---|
| 제목 H1~H6 | 필수 | ATX 헤딩 우선 |
| 단락·줄바꿈 | 필수 | 원문과 렌더링 의미 동등성 |
| 굵게/기울임/취소선 | 필수 | GFM 취소선 |
| 링크 | 필수 | URL scheme 검증 |
| 목록·중첩 목록 | 필수 | 들여쓰기 테스트 |
| 체크박스 | 필수 | GFM 작업 목록 |
| 인용문 | 필수 | 중첩 인용은 변환 테스트 |
| 코드 블록/인라인 코드 | 필수 | 언어명 보존 |
| 표 | 필수 | 복잡한 병합 셀은 제외 |
| 이미지·ALT 텍스트 | 필수 | 로컬 상대경로 |
| 수평선 | 필수 | 구문 지원 |
| HTML 포함 Markdown | 제한 | 원문은 보존 가능, 미리보기 렌더링은 안전 정제 |
| 각주, 수식, Mermaid | 후속 | P1에서 필요성·호환성 평가 |
| 실시간 댓글·멘션·DB 뷰 | 제외 | 표준 MD에 직접 표현 곤란 |

### 7.2 Round-trip 품질 게이트

- Markdown → AST/에디터 → Markdown 변환 테스트를 자동화한다.
- **텍스트 바이트 단위 동일성**은 요구하지 않음(공백·줄바꿈·목록 마커가 정규화될 수 있음).
- 의미적 동등성(헤딩 깊이·문장·표 행/열·체크 상태·링크 URL·이미지 경로·코드 본문)이 필수.
- 지원하지 않는 노드는 무단으로 삭제하지 말고 편집 잠금/원문 보존/사용자 안내 중 하나로 처리.
- 원문에 포함된 HTML 주석 또는 비표준 확장은 시각적 모드에서 손실 위험이 있으므로 별도 테스트 및 보존 전략 필요.
- raw Markdown 모드와 WYSIWYG 모드 전환 시 변경점 diff를 검사할 수 있는 내부 디버그 기능 확보 권장.

### 7.3 문서 링크

V1에서는 일반 Markdown 상대 링크를 지원한다.

```markdown
[분석결과](분석결과/결과요약.md)
[참고 PDF](assets/01JXXXX-report.pdf)
```

V1.5에서 내부 링크 생성 UI와 문서 ID 매핑을 추가한다. `[[문서명]]` 식 비표준 문법은 도입하더라도 표준 Markdown으로 내보내는 규칙을 반드시 정의한다. 문서 이름 변경 또는 이동 시 참조 경로 자동 갱신은 단위 테스트로 검증한다.

### 9.3 기업용 보안 확장(V2~V3)

- 인증 서버, 조직·프로젝트별 접근 통제(RBAC/필요시 ABAC).
- TLS 전송, 서버 저장 시 암호화 정책, 장치 관리, 비밀관리 서비스.
- 파일별 접근 이벤트 및 감사 대상 정의.
- 전자결재 후 문서 원본은 대표이사 포함 누구도 직접 수정할 수 없도록 잠금.
- 변경 시 개정본을 생성하고 이전 버전·승인 이력·변경 사유를 보존.
- 감사 로그는 임직원이 부여받은 범위에서 열람, 정책·설정 변경은 대표이사 전용.
- 이미 적재된 감사 이력의 수정·삭제 방지는 단독 로컬 DB만으로 성립하지 않으므로 독립 보존소, 불변 스토리지 또는 외부 타임스탬프·서명 등의 체계를 검토.
- 다중 사용자 협업 환경에서는 서버 측 권한 검증이 필수. 클라이언트 UI 숨김만으로 보안을 구현하지 않는다.

### 9.4 비공개와 공개 게시의 분리

- 기본값은 **모든 문서 비공개**.
- 공개 문서 게시 기능(V1.5)을 만들 경우 문서 단위 승인 목록과 첨부파일 점검 필수.
- 게시 시 메타데이터, 경로, 이미지 EXIF, 내부 링크, 주석, 숨겨진 문서 참조까지 검사.
- **비공개 Git 저장소에 소스 코드를 보관하는 것과 게시된 웹사이트의 비공개성은 별개**임을 운영 정책에 명시.

## 10. 향후 동기화 설계(V2 인터페이스 요구사항)

> **V1에서 구현하지 않지만, V1 저장 방식이 V2 동기화를 어렵게 만들지 않도록 아래 식별자·revision 계약을 지킨다.**

### 10.1 데이터 동기화 단위

- 문서: `document_id`, `revision`, `checksum`, `updated_at`, `deleted_at` 또는 tombstone.
- 첨부파일: `asset_id`, 해시, MIME, size, blob 저장 위치.
- 프로젝트·폴더: 안정적인 ID, parent 관계, 경로 변경 이벤트.
- 서버는 문서 본문과 첨부파일을 버전 단위로 받아 기존 revision과 비교.

### 10.2 충돌 원칙

- 마지막 수정시각만으로 무조건 덮어쓰기 금지.
- 서버 `revision`과 클라이언트 `base_revision`이 불일치하면 충돌로 판단.
- V2 초반에는 복제본 생성 또는 사용자 병합을 제공; 자동 CRDT 공동편집은 별도 평가.
- 삭제도 tombstone으로 동기화하여 삭제된 문서가 다른 기기에서 무단 부활하지 않도록 처리.
- 오프라인 편집은 동기화 큐에 쌓되, **로컬 저장 성공과 서버 반영 성공은 다른 상태**로 표시.

### 10.3 서버 선택 기준

- Google Drive/OneDrive/S3는 보관 계층으로 활용할 수 있지만 **그 자체가 문서 충돌 해결·버전 정책·권한 모델을 완성해 주지는 않는다**.
- 스토리지 연결 시 벤더별 어댑터를 분리하고 데이터 포맷은 유지.
- 서버 필요조건: 인증, 변경 목록·revision API, 충돌 응답, 첨부 스토리지, 암호화, 감사, 백업.
- 로컬 네트워크 PC 서버를 선택할 경우 기기 전원·네트워크 가용성·외부 접속 보안 정책이 추가 필요.

### 10.4 예상 API 계약(예시, V2)

```http
GET    /api/v1/workspaces/{workspaceId}/changes?cursor=...
GET    /api/v1/documents/{documentId}
PUT    /api/v1/documents/{documentId}       # If-Match: revision
POST   /api/v1/assets                    # 업로드 세션 또는 서명 URL
GET    /api/v1/assets/{assetId}
POST   /api/v1/sync/commit               # 변경사항 batch 제출
```

API는 향후 인증·인가, pagination, idempotency key, 오류 코드, 중복 요청 안전성 기준을 포함해 별도 문서화한다.

## 11. 추후 기능 확장(V3~V4)

### 11.1 전자문서·전자결재

- 문서 상태: `draft -> review -> approved -> superseded` 등 명시적 상태기계.
- 결재 완료 시 원본 불변 정책 적용, 새 개정본 작성으로 변경.
- 승인자, 승인 시각, 승인 대상 revision/checksum, 승인 사유 보존.
- 대표이사 전용 감사 정책·권한 설정, 허용된 직원별 조회 범위.
- 기업 문서번호·전자서명·승인 이력·내보내기 등은 별도 법률·운영 요건 검토 후 구현.

### 11.2 AI/RAG 통합

- 문서와 첨부파일의 내용을 권한 범위에서 인덱싱.
- 문서 ID, 파일 경로, revision, 구간 위치를 출처 메타데이터로 보존.
- AI 검색 결과는 원문 링크·참조 구간을 제시.
- 비공개 문서를 외부 모델에 보내는지에 관한 정책·승인·로그 확보.
- AI 생성 내용은 자동으로 승인 문서에 반영하지 않음.
- 로컬 모델과 클라우드 모델을 `AIProvider` 인터페이스로 분리할 수 있도록 설계.

**PRESTIQUE Workspace V1은 별도 서버에 의존하지 않는 로컬 우선 Markdown 문서관리 프로그램으로 구축한다.** Windows 데스크톱 앱에서는 사용자가 소유하는 `.md` 파일과 첨부를 로컬 폴더에 저장하고, 동일한 문서 편집 엔진을 사용한 웹/PWA 앱은 GitHub Pages 등 정적 호스팅에서 실행되되 브라우저의 로컬 저장소를 이용한다. 모바일에서는 Markdown 문법을 입력하지 않아도 사진 촬영·첨부와 시각적 글쓰기를 할 수 있다. 두 저장소의 자동 동기화는 V2에서 구현한다. 초기 개발은 문서 무결성·휴대성·백업·오프라인 작업을 최우선으로 하고, 전자결재·권한·감사·AI는 확장 가능한 인터페이스를 유지하면서 후속 단계에서 구현한다.

**디자인 정책:** 본 문서에는 시각 디자인 요구사항을 포함하지 않는다. 별도의 디자인 문서로 정의한다.
